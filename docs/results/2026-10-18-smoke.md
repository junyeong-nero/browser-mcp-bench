# GPT-6.1-Sol: first real browser MCP smoke pair

Date: 2026-10-18. **Integration evidence only, not a benchmark score or ranking.**

## Conditions

- Codex CLI: `0.163.0`, existing ChatGPT subscription login; no API-key fallback.
- Model: `gpt-6.1-sol`; reasoning effort: `medium`.
- The installed model catalog explicitly listed this ID and `medium` support.
- Common developer instructions, task, 180-second wall-clock limit, and run
  policy. Fresh Codex task sessions and temporary working directories.
- Exactly one configured MCP name, `browser`, using each server's native tools.
- Playwright MCP: `0.0.83`, local npm dependency pinned by `package-lock.json`.
- Playwright runtime: `1.64.0-alpha-1790635538000`.
- Kitsune: clean source revision `967dfdf6babba27383cfdab4a2997f2dfcb57c76`,
  invoked with `uv run --locked --project`.
- Both targets used the same private-cache Firefox156.0 executable (build1553),
  headless, with separate fresh profiles. Effective viewport parity was not
  measured; only Playwright has an explicit 1280x720 viewport configuration.
- Kitsune used web-ext10.8.0 to install a temporary extension in a fresh profile,
  private bridge HTTP/WS ports, private `KITSUNE_HOME`, and an ephemeral token.
  Only the private extension copy's WebSocket URL was changed. The source
  extension hash remained unchanged after execution.

## Task

`tasks/smoke/example-domain.json`: open `https://example.com` in a new tab and
report the heading and the destination of the “Learn more” link. Do not change
unrelated tabs/accounts or submit forms.

Both final answers reported:

- No heading element present; page title: `Example Domain`.
- Link destination: `https://iana.org/help/example-domains`.

The actual MCP tool results also contained this title and destination. This was
manually inspected evidence, not a separate automated evaluator. No success
rate or formal success label was assigned.

## Setup failures and corrections

Two earlier real Playwright model executions were integration failures and are
**excluded from the final pair table**, not silently counted as successes:

1. MCP new-tab action required approval while the noninteractive policy was
   `never`. The selected server now explicitly auto-approves its native tools;
   non-MCP bypass tools remain disabled.
2. Playwright initialization exceeded the macOS Unix-domain socket path limit.
   The smoke wrapper now supplies a private short `PWTEST_SOCKETS_DIR`.

Additional browser lifecycle checks used a mocked agent call, with no model
inference. They exposed a macOS process-group cleanup race; cleanup now waits a
bounded period after EPERM and only accepts it when no live group member remains.
Codex warning/error items are parsed as diagnostics, not mislabeled as tools;
real error items still mark harness errors. The unstable feature warning is
suppressed per run rather than changing the user's config.

The initial plain Playwright install unexpectedly garbage-collected shared
Chromium caches for builds1187/1243 and their headless shells. These were
automation caches, not user profiles. The new installation helper uses a private
cache and disables garbage collection to avoid repeating this side effect.

## Limits on interpretation

- One very simple task, one attempt per target, fixed Playwright-first order.
- Public page drift remains possible; this is not a resettable environment.
- Prompt caching, latency variance, and tool selection were not counterbalanced.
- Kitsune's browser/bridge startup occurred before its timed agent run;
  Playwright may initialize its browser during a timed MCP call. These numbers
  are not a controlled comparison of total cold-start latency.
- Same Firefox executable does not prove identical viewport/preferences or
  extension effects. No complete model-visible prompt/tool-catalog attestation.
- No independent automated task evaluator, scored benchmark dataset, repeated
  runs, confidence intervals, or complete infrastructure-failure taxonomy.

**Conclusion:** the subscription-backed Codex → browser MCP execution path works
for both targets in isolated Firefox profiles. The next milestone is a fixed
resettable task subset with an independent evaluator, then repeated paired runs
with controlled order. Do not generalize this table into an agent leaderboard.

## Reproduce

From the repository root, with Codex login, Node/npm, uv, and the Kitsune checkout:

```sh
uv sync --locked
npm ci --ignore-scripts --no-audit --no-fund
npm run setup:firefox
uv run --locked python -m kitsune_benchmark smoke            # inspect only
uv run --locked python -m kitsune_benchmark smoke --execute  # real quota usage
```

The current runner additionally collects process resources; the original table
above predates that collector. Use the lockfile environment for current code.

The smoke pins are in `configs/experiments/smoke.json`. Use
`--kitsune-project /absolute/path/to/kitsune` if it is not the sibling checkout.
